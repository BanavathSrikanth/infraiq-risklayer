# Risk BFF API Guide

This guide describes the five risk endpoints currently exposed by the .NET BFF,
how each request travels to the Python Risk Service, what the Python service
does, and what the caller receives.

## Services and request path

- Swagger UI: `http://localhost:5085/swagger` (Development environment only).
- .NET BFF default Python service URL: `http://localhost:8000`, configurable
  with `RiskServiceUrl`.
- The BFF exposes `api/v1/risks/...` routes and calls the matching Python route
  over HTTP using a typed `HttpClient` with the standard resilience handler.
- The BFF is a gateway; risk calculations, persistence, cache access, and
  priority scoring are owned by Python.

Normal request path:

```text
Client or Swagger -> .NET BFF :5085 -> Python Risk Service :8000
                                      -> response -> BFF -> caller
```

The BFF currently does not authenticate callers or derive `tenant_id` from a
validated identity. Treat caller-supplied tenant IDs as untrusted until that is
implemented.

## 1. Calculate risk

**Route:** `POST /api/v1/risks/calculate`

**Purpose:** Calculate a risk evaluation for one asset from JSON input.

**Request:** Supply `asset_id`, `tenant_id`, and the required `ahs`, `ces`,
`cqs`, and `ves` sections. Weather, hazard, and feed-status fields are also
accepted; some have defaults. Scores and enum values are validated by Python.

Example request:

```json
{
  "asset_id": "pole-1001",
  "tenant_id": "tenant-demo",
  "ahs": {
    "age_years": 18,
    "material": "wood",
    "remaining_fiber_pct": 68,
    "defect_severity": "moderate",
    "lean_deg": 2.5,
    "attachment_count": 7,
    "asset_class": "distribution",
    "reinforced_within_10_years": false
  },
  "ces": {
    "hftd_tier": "tier_2",
    "fhsz_level": "high",
    "landfire_ros_class": 3,
    "slope_deg": 12,
    "p95_historical_gust_mps": 22
  },
  "cqs": {
    "population_density_1km": 900,
    "critical_facilities_2km": 2,
    "customers_on_circuit_segment": 85,
    "road_density": 0.6
  },
  "weather": {
    "wind_speed_mph": 16,
    "temperature_f": 82,
    "relative_humidity_pct": 35,
    "precipitation_in": 0,
    "fire_weather_index": 45
  },
  "time_sensitivity": 30,
  "days_overdue": 12,
  "work_already_scheduled": false,
  "stale_feeds": [],
  "imputed_feeds": [],
  "missing_feeds": [],
  "critical_missing_feeds": [],
  "ves": {
    "proximity_factor": 0.7,
    "density_factor": 0.5,
    "clearance_factor": 0.6,
    "overlap_factor": 0.4,
    "encroach_factor": 0.3
  },
  "hazard_exposures": []
}
```

**Flow:** The BFF accepts the JSON and forwards it unchanged to Python's
`POST /api/v1/risks/calculate`. Python validates it, calculates AHS, CES, CQS,
DHM, OPS, VES, the composite risk score/category, confidence, and explanation.
The configured v1.1 composite score uses AHS, CES, CQS, and VES weights. Python
appends the evaluation to risk history and attempts to cache it in Redis for
300 seconds. The result is returned through the BFF.

**Response:** A JSON risk evaluation. Important fields include
`risk_evaluation_id`, `asset_id`, `tenant_id`, `risk_score`, `risk_category`,
`ahs`, `ces`, `cqs`, `dhm`, `ops`, `ves`, `calculation_version`,
`input_values`, `explanation`, `confidence`, `stale`, and `warnings`. The
evaluation ID is generated by Python and can be used for pole-priority input.

**Errors:** Python validates the input and can return a validation error (often
HTTP 422). The current BFF client calls `EnsureSuccessStatusCode()` for this
route, so non-success responses are not explicitly passed through as upstream
responses and may surface as a BFF 500.

## 2. Ingest risk CSV from Blob Storage

**Route:** `POST /api/v1/risks/ingest/blob`

**Purpose:** Process multiple assets from a CSV blob that already exists in the
configured Azure Blob Storage container. This endpoint does not upload a file.

Python request contract:

```json
{
  "blob_name": "risk-inputs/sample-risk-data.csv",
  "tenant_id": "tenant-demo"
}
```

Python expects a UTF-8 CSV with a header row. Nested field names use dotted
paths, for example `ahs.age_years`, `ces.hftd_tier`, `cqs.road_density`, and
`ves.proximity_factor`. Each CSV row represents one risk input. Python
validates, calculates, and appends each valid row to risk history separately;
invalid rows are reported without stopping other rows from processing. If a
request tenant is supplied, each row's `tenant_id` must match it.

**Response from Python:** `blob_name`, `records_received`,
`records_processed`, `results`, and row-numbered `errors`.

**Current BFF caveat:** `RiskIngestRequest` and `RiskIngestResponse` do not
currently map all Python field names and response fields. The request DTO has
`BlobName`/`TenantId` without explicit `blob_name`/`tenant_id` JSON names, while
Python requires snake_case. The response DTO contains only `results` and
`errors`, so counts and `blob_name` are omitted. Align these DTOs before relying
on blob ingestion through the BFF. The BFF client also uses
`EnsureSuccessStatusCode()`, so Python error statuses are not explicitly
forwarded.

Python may return 503 when Blob Storage is not configured, 400 for an invalid
CSV/tenant mismatch, or 502 for a blob download/ingestion failure.

## 3. Get latest risk for an asset

**Route:** `GET /api/v1/risks/latest/{assetId}?tenant_id={tenantId}`

Example:

```text
GET http://localhost:5085/api/v1/risks/latest/pole-1001?tenant_id=tenant-demo
```

**Flow:** The BFF URL-escapes the asset ID and tenant ID and forwards them to
Python's matching GET route. Python first looks up the latest evaluation in
risk history. If none is found there, it checks Redis using the tenant and
asset key. If neither contains a result, Python returns 404. The BFF forwards
the Python response body, content type, and HTTP status.

**Response:** One risk evaluation in the same shape as the calculate response.

## 4. Calculate pole priority

**Route:** `POST /api/v1/risks/pole-priority`

**Purpose:** Produce an advisory priority score for routing/planning work. It
does not authorize or assign work and does not persist a priority evaluation.

Example request (use the evaluation ID and score from a calculate/latest
response):

```json
{
  "asset_id": "pole-1001",
  "tenant_id": "tenant-demo",
  "risk_evaluation_id": "<risk-evaluation-id-from-calculation>",
  "risk_score": 43.23,
  "hazard_exposure": 35,
  "consequence_score": 25,
  "treatment_urgency": 50,
  "inspection_confidence": 90
}
```

The BFF request model explicitly maps these snake_case JSON names to .NET
properties. All five numeric score inputs must be between 0 and 100. Python
weights risk score 0.40, hazard exposure 0.25, consequence 0.20, treatment
urgency 0.10, and inspection confidence 0.05. It returns the calculated score,
priority band, contributing factors, evaluation ID/time, and rule version.
Bands are `low` below 40, `medium` from 40, `high` from 70, and `critical`
from 90. The BFF forwards the Python response body and status.

## 5. Get risk history for an asset

**Route:** `GET /api/v1/risks/history/{assetId}?tenant_id={tenantId}`

Example:

```text
GET http://localhost:5085/api/v1/risks/history/pole-1001?tenant_id=tenant-demo
```

**Flow:** The BFF forwards the asset ID and tenant query value to Python. Python
queries persisted risk evaluations for that tenant and asset and returns them
as a JSON array. An asset with no recorded evaluations returns an empty array
with HTTP 200. The BFF forwards the Python response body, content type, and
status.

## How the five endpoints fit together

1. Use `POST /calculate` for one JSON asset, or `POST /ingest/blob` for a CSV
   batch (the latter needs the BFF DTO contract caveat fixed and Blob Storage
   configured).
2. Save the returned `risk_evaluation_id` and `risk_score`.
3. Use `GET /latest/{assetId}` to fetch the latest result, or
   `GET /history/{assetId}` to fetch all persisted evaluations for the tenant.
4. Use `POST /pole-priority` with an evaluation ID and the relevant 0-100
   priority factors to compute an advisory work-priority score.

Run Python on port 8000 and the BFF on port 5085. The interactive BFF API
surface is available at `http://localhost:5085/swagger` while the BFF is in
Development mode.
